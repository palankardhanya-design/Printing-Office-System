The Printing Office

Print Queue Consolidation System — K-Way Merge via Linked Lists & Min Heap

This system consolidates print jobs from multiple departments into a single ordered timeline. Each department maintains its jobs in a singly linked list (sorted by submission time), and a min-heap orchestrates the K-way merge — always extracting the job with the smallest timestamp. When timestamps tie, jobs are ordered lexicographically by department code, producing a deterministic, fair output in O(N log K) time.

💡 Demonstration Mode — FAQ

Technical deep-dive into the algorithm design decisions.

Linked lists are ideal here because we only ever consume jobs from the front of each department's queue — a pure FIFO access pattern. Unlike arrays, a singly linked list allows O(1) removal of the head node without shifting elements. Memory is also allocated only for the jobs that exist, avoiding wasted capacity. This matches the real-world model where new print jobs arrive and are appended, while the merge engine always pulls the smallest pending job from the front.

A min-heap maintains the global minimum across all department queues in O(log K) time per operation, where K is the number of departments. The root of the heap is always the job with the smallest submission time, so each extraction takes O(log K) for the subsequent heapify-down. The alternative — scanning all K department heads every extraction — would cost O(K) per step and O(NK) overall, which degrades badly as departments grow. The heap gives us guaranteed O(N log K) total time regardless of input distribution.

The heap needs to hold at most one candidate per department at any time — the current smallest unprocessed job. Inserting all jobs upfront would bloat the heap to size N, making every heapify operation O(log N) instead of O(log K). By inserting only the head of each department's linked list, the heap stays bounded at size K throughout the entire merge. This is the key insight that keeps space complexity at O(K) rather than O(N).

When a job is extracted from the heap and appended to the merged timeline, its department's queue advances by one node. The next job in that department's linked list (if it exists) is then inserted into the heap as the department's new representative. This "lazy replenishment" strategy ensures the heap always holds the current minimum candidate from each active department — no earlier, no later. This is what keeps the heap size at exactly K and maintains the O(N log K) guarantee.

When two or more jobs have identical submission times, the min-heap's comparator breaks the tie using lexicographic ordering of department codes (e.g., "A" < "B" < "C"). This is a deterministic, fair policy — departments with alphabetically earlier codes get priority for equal-time jobs. If two jobs from the same department somehow tie (impossible in a valid sorted-per-dept input), the original position index serves as a final tiebreaker. The result is a fully deterministic, reproducible merged output.

When a department's last job is extracted from the heap, there is no successor node to insert. The department simply stops contributing candidates to the heap. The heap size decreases by one, and subsequent operations are slightly faster. The merge continues with the remaining K′ < K active departments until the heap is completely empty, at which point the merged timeline is complete. Empty departments (queues with zero jobs) are skipped entirely during initialization.

There are N total jobs, and each job participates in exactly one heap insertion and one heap extraction. Each heap insertion triggers a heapify-up pass of at most ⌊log₂ K⌋ comparisons/swaps, and each extraction triggers a heapify-down of the same depth. The heap height is bounded by log₂ K because the heap never holds more than K elements. Therefore the total work is 2 × N × O(log K) = O(N log K). The N log K formula is tight — you can verify it empirically by comparing the comparison count from the stats panel against N × ⌊log₂ K⌋.

A naïve approach would collect all N jobs into a single array and sort them — O(N log N) in the best case. But a truly naïve merge that repeatedly scans all queues to find the minimum runs in O(NK) time. Even if you sort each newly extracted batch, re-sorting a growing list after each insertion yields O(N² log N) in the worst case. The heap approach avoids all redundant comparisons: once a job's relative position is established by the heap structure, it is never re-compared unless a new job from its department challenges it. For large N and small K, the difference is orders of magnitude in practice.
